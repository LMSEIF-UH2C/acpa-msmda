# Codebook de validation des identités — V0.1 proposée
Objectif : qualifier la relation entre deux identifiants de source distincts. Ce jugement est indépendant de la pertinence EPS et de la cotation 10D/97P. S'applique au kit 57 paires du pilote, tiré sur les signaux disponibles; aucune décision n'est préremplie. Les 13 paires intersources sont toutes incluses. Les juges doivent être humains, indépendants et travailler sans accès aux décisions de l'autre. Les relations directionnelles sont codées du point de vue de A vers B. Si plusieurs relations sont plausibles, retenir la relation principale la plus précise et justifier; si impossibilité de trancher, UNCERTAIN.
| Code | Définition | Preuve minimale attendue |
|---|---|---|
| SAME_PRODUCT | Même produit distribué sous identités/variantes distinctes; renommage continu prouvé | Documentation officielle reliant les variantes ou l'ancien et le nouveau nom, identité d'éditeur et continuité; un dépôt n'est pas une distribution de produit |
| DISTINCT_PRODUCT | Produits distincts, homonymes ou dépôts sans relation démontrée après vérification suffisante | Preuves distinctives documentées; un défaut de preuve seul ne suffit pas |
| A_SOURCE_CODE_OF_B / B_SOURCE_CODE_OF_A | Dépôt source de l'application, ou relation de code explicitement établie | Lien de code publié par le projet et correspondance de l'application; ne pas convertir en SAME_PRODUCT |
| A_FORK_OF_B / B_FORK_OF_A | Dérivation identifiée, pas identité | Documentation du fork ou historique de dépôt, sans supposer qu'il est équivalent |
| A_COMPONENT_OF_B / B_COMPONENT_OF_A | Extension/module ou composant d'une suite/projet | Documentation de l'architecture ou du produit |
| A_SUCCESSOR_OF_B / B_SUCCESSOR_OF_A | Remplacement documenté par un produit distinct | Annonce officielle de migration ou de remplacement; renommage continu = SAME_PRODUCT si établi |
| UNCERTAIN | Preuves insuffisantes, contradictoires ou accès impossible | Motif explicite, URL si consultable |
Pour SAME_PRODUCT, les deux entités doivent être des distributions de produit, pas un dépôt GitHub du pilote. Les forks, modules, successeurs distincts et codes sources restent séparés. Interdire propagation d'identité par transitivité en présence de contradictions; avant fusion, contrôle du groupe entier. Étiqueter la variante distinctement.
## Procédure
1. Télécharger les deux CSV vierges depuis l'[artefact](https://github.com/LMSEIF-UH2C/acpa-msmda/actions/runs/46133860479/artifacts/15258718327); conserver review_id, stratum, source_a, id_a, source_b, id_b, signals sans modification. Ne pas modifier la décision de l'autre juge. 
2. Retrouver la page officielle : Apple https://apps.apple.com/app/id{trackId}, F-Droid https://f-droid.org/packages/{package}/, GitHub API https://api.github.com/repositories/{repositoryId} (résoudre vers le dépôt officiel). Ces modèles ne garantissent pas l'accessibilité. Vérifier noms, éditeurs, identifiants, versions, documentation de provenance et éventuels liens explicites. Ne pas conclure à partir du signal généré.
3. Renseigner decision, evidence_url (URL officielle principale, compléter les liens dans justification), evidence_date (ISO AAAA-MM-JJ), justification concise; UNCERTAIN exige justification et date, URL facultative si indisponible. Aucune description commerciale intégrale, aucun compte personnel ni collecte privée. Verrouiller les fichiers remplis et conserver les empreintes avant comparaison.
4. Comparer les deux décisions exactes (direction comprise), accord brut, kappa nominal multiclasse et matrice de confusion, puis arbitrage documenté. Distinguer l'accord de l'exactitude. Pour l'évaluation d'une règle de fusion, la référence arbitrée définit TP/FP/FN; ne jamais compter UNCERTAIN comme vrai négatif. Signaler les cas indéterminés, et les limites des effectifs.
5. Préparer un ensemble indépendant de validation contenant aussi paires non générées, cas multilingues, renommages connus, homonymes et groupe différé de 63. Échantillonnage et seuils confirmatoires à préenregistrer, avec stratification/pondération si l'on veut estimer des performances globales. Le kit candidat n'est pas une mesure de rappel; examiner les faux négatifs par recherche indépendante de variantes pour un ensemble de produits.
6. Aucun produit fusionné automatiquement à ce stade, même si deux juges concordent : arbitrage/contrôle de contradictions et décision de l'équipe avant construction du registre produit. 
## Cas de formation (illustratifs, pas des résultats du pilote)
Deux applis de chronométrage homonymes ne sont pas nécessairement un produit; une application et son code sont liés mais non identiques; un dépôt peut héberger de nombreux composants; une suite bureautique contient des produits distincts; un renommage documenté peut conserver l'identité. 
Statut : codebook proposé pour calibration; validation par les juges et équipe requise. Ne pas modifier la grille après lecture des résultats confirmatoires sans amendement versionné.
